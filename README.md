# Kryon

> **The security layer for AI-built software.**

Hypothesis-driven autonomous multi-agent framework for safe and verifiable security research. Built for the era when AI ships code in hours, not weeks.

*Project name is a placeholder. Code is name-agnostic — rename anytime via `kryon config`.*

---

## The problem

AI is changing how software gets built. Code that used to take a team of engineers months to produce can now be written by an AI agent in a single afternoon. "Vibe coding" — describing what you want in natural language and letting an LLM generate the implementation — has become the default mode of software development for many teams.

But the speed of AI building has outpaced the speed of security testing. The traditional pentest pipeline takes days or weeks. By the time a vulnerability is found, the AI has already shipped three more versions of the same code. Worse, the vulnerabilities themselves are often generated by the same AI that wrote the code — the LLM doesn't know which patterns are dangerous unless it's been explicitly told, and even then, it doesn't always remember.

The result: a growing class of AI-built software that ships with unverified vulnerabilities. SQL injection, IDOR, SSRF, exposed admin endpoints, leaked API keys, missing authentication, broken access control — the same old security failures, now produced at machine speed.

The industry is catching up. Static analysis tools, AI code review bots, and security linters have proliferated. They help, but they share a common limitation: they look for patterns, not for *exploitable behavior*. A pattern matcher can flag a SQL query that uses string concatenation; it can't tell you whether the parameter is actually injectable, whether the database is reachable, or whether the response includes a useful error message. It catches signatures, not vulnerabilities.

What security needs in the AI era is not just faster scanning. It needs **autonomous reasoning** — a system that can think like a senior pentester, propose testable claims, run real exploits, demand evidence, and only then report a finding. A system that can match the speed of AI-built code without sacrificing the rigor of a real security test.

## The risks

When software ships with unverified vulnerabilities, the consequences compound. The risks are not theoretical — they're the same risks that have always existed, but at higher volume and shorter detection time.

**Unverified exploits reach production.** A SQL injection that the framework "kind of" handles correctly. An IDOR that returns data when the user is authenticated as the wrong role. A stored XSS that fires in some browsers but not others. These aren't theoretical — they're shipped to real users every day. When the first real attack comes, the team has no prior warning.

**The "we'll fix it later" tax.** Every unverified vulnerability becomes a backlog item. Every backlog item has a context-switching cost for the engineer who eventually fixes it. Every fix has a regression risk. The math doesn't work: AI builds fast, but engineers still fix one bug at a time. Backlog compounds.

**No defensive artifacts.** Even when a vulnerability is eventually found and fixed, the defense layer is often an afterthought. The team patches the code, maybe adds a WAF rule, and moves on. There's no detection rule that fires when the attack is attempted. There's no incident response playbook. The next attacker gets to find the same bug first.

**False positives erode trust.** Generic scanners produce noise. When half the reported vulnerabilities turn out to be WAF block pages or unreachable endpoints, engineering teams stop trusting the security tooling. They ignore alerts. They deprioritize patches. The defensive posture quietly degrades.

**Compliance gaps.** For companies in regulated industries, the lack of an auditable security testing process is itself a compliance issue. A system that doesn't produce evidence — that can't answer "did we test this?" with proof — is a liability.

**No provenance.** When a security test is run by a human pentester, you have a person to ask. When it's run by an LLM agent, you need a structured record of what was tested, what was found, and how. Without that record, the test is a black box, and black boxes are hard to defend in a post-incident review.

The risks are not new. What's new is the *volume* — AI builds more code, faster, with the same vulnerabilities as before, and the security pipeline hasn't scaled to keep up.

## The solution

Kryon is a **hypothesis-driven autonomous multi-agent framework for security research**. It's designed to do for security testing what AI coding tools have done for software development: make it faster, more thorough, and more reproducible, without sacrificing rigor.

The core idea is **structure enables autonomy**. Most LLM agent systems are too permissive — they let the AI improvise freely, which produces noise. Kryon constrains the AI with a **typed contract at every step**:

- Before any exploit runs, the LLM must produce a structured **Hypothesis** with a `precondition`, `reasoning`, `test_plan`, `expected_evidence`, and honest `confidence_prior`. The LLM cannot just say "maybe there's XSS somewhere." It has to make a concrete, testable claim.
- Every subagent has a **specific role** (recon, exploit, verify, defend) and a **limited permission set** (only the `verify` subagent can write a `Finding` node, even a buggy exploit agent cannot promote itself).
- Every action is **logged immutably** to an append-only audit trail, with cost and duration attached. The system can be paused, resumed, and replayed.

The output isn't just a list of vulnerabilities. It's a **purple team** output: every offensive finding is paired with a working **Sigma detection rule** and an **incident response playbook**. The red team and the blue team, in the same loop.

The result: a security testing system that can run at AI speed, reason like a senior pentester, and produce auditable, defensive output — not just bug reports.

## Features

- **8 specialized subagents** with distinct roles, system prompts, and permission sets
- **9-state explicit loop** — every state is auditable, every transition is checkpointed
- **Typed Hypothesis schema** — the LLM must produce structured output before any exploit can run
- **Permission-enforced knowledge graph** (KùzuDB) — only the `verify` subagent can write `Finding` nodes
- **Append-only audit log** — SQLite with DB-level triggers blocking `UPDATE`/`DELETE`
- **66 security tools** in the registry, all running in isolated Docker containers
- **Network isolation per tool** — `none` / `passive` / `active` / `oob` modes
- **LLM-agnostic** via LiteLLM (Anthropic, OpenAI, Azure, Bedrock, Ollama, custom)
- **Budget tracking** — hard caps on cost, iterations, and wall-clock time
- **Pause / resume** via checkpoints — no lost work, no runaway spend
- **MIT licensed** — open source

## The 8 Agents

Kryon's reasoning layer is a team of 8 specialized subagents. Each has a role, a permission boundary, and a personality in how it works.

### recon-passive — *The Observer*

Watches the target from a distance. Never sends a single packet to the target. Uses certificate transparency logs, DNS aggregators, public breach databases, and GitHub code search to discover subdomains, leaked credentials, exposed services, and historical endpoints. The work happens in third-party data sources, not the target itself.

**Writes to the graph**: `Asset`, `Tech`, `Person`, `Credential`

### recon-active — *The Scanner*

Probes the live attack surface. Sends traffic under a configurable rate limit. Discovers open ports, running services, web endpoints, parameters, and technologies. Stays inside scope, respects rate limits, never attempts exploitation.

**Writes to the graph**: `Asset`, `Endpoint`, `Tech`, `Person`, `Credential`

### analysis-hypothesis — *The Thinker*

The structural innovation. Reads the knowledge graph and emits typed `Hypothesis` objects. Each hypothesis must include:

- **precondition** — what must be true for this to be exploitable
- **reasoning** — why this might work, citing the specific tech, parameter, and auth state
- **test_plan** — step-by-step: 1. Send X. 2. Observe Y. 3. Confirm Z.
- **expected_evidence** — what success looks like (specific strings, status codes, behaviors)
- **confidence_prior** — honest 0.0–1.0 score

The LLM cannot just say "maybe there's XSS somewhere." It has to make a concrete, testable claim. The system tracks existing hypotheses and prioritizes new ones by expected impact and confidence.

**Writes to the graph**: `Hypothesis` only

### exploit — *The Attacker*

Executes the test plan. Captures evidence. Runs the actual security tools — the ones in the registry, the ones the LLM requested via the `tool_calls` field of its structured output. Captures raw tool output, exit codes, durations.

Critically, **cannot promote itself to a Finding**. That's the verify subagent's job. The exploit subagent produces `ExploitAttempt` records — what it tried, what happened, what the evidence was — and passes them forward.

**Writes to the graph**: `ExploitAttempt` only

### post-exploit — *The Chainer*

Looks for ways to combine confirmed findings into exploit chains. Demonstrates compounded impact: the IDOR plus the admin endpoint exposure equals full user data access. Surfaces new assets discovered during pivoting.

**Writes to the graph**: `ExploitChain` only

### verify — *The Judge*

**The trust boundary.** The only subagent allowed to write `Finding` nodes. Re-runs the exploit, demands reproduction (at least two times), uses a *second independent method* to confirm, checks for false positives, and assigns severity honestly.

The verify subagent follows hard rules:
- Reproduce at least twice. A single tool's claim is not evidence.
- Use a different method than the original exploit. If the original used sqlmap, verify must also use manual curl, or Burp, or a hand-crafted payload.
- Reject if the "evidence" is just a tool's claim without raw output.
- Reject if the vulnerability requires out-of-scope access to exploit.
- Reject self-XSS, missing auth (different from broken auth), WAF block pages, custom 404s.
- Assign severity honestly. No marketing "critical vulnerability" hype.

When verify confirms a finding, it becomes a `Finding` node in the graph. When it rejects, the hypothesis is updated to "rejected" with a reason.

**Writes to the graph**: `Finding` only

### blue-team — *The Defender*

For every confirmed Finding, generates two artifacts:

- A **working Sigma detection rule** (valid YAML, specific to the exploit pattern, not boilerplate). The rule has a clear logsource, a specific detection, a false-positive consideration, and a level that matches the finding severity.
- An **incident response playbook** (markdown, with concrete steps for triage, containment, eradication, recovery, and lessons learned). The playbook references specific log queries, specific WAF rules, specific patch instructions.

Each defensive artifact is mapped to MITRE ATT&CK techniques.

**Writes to the graph**: `DefensiveArtifact`, `SigmaRule`, `IRPlaybook`

### report — *The Storyteller*

Synthesizes everything — findings, exploit chains, defensive artifacts, narrative — into a professional report. Outputs Markdown, JSON, and HTML. Executive summary for leadership. Full technical detail for the engineers. No marketing fluff, no fabricated severity, every claim backed by a confirmed Finding.

**Writes to the graph**: Nothing. The report goes to the filesystem, not the graph.

## The 9-State Learning Loop

The agents don't run independently. They run as a coordinated team inside an explicit 9-state loop. Each state maps to a subagent. Each transition is auditable. Each step saves a checkpoint.

```
INIT
  ↓
RECON_PASSIVE       (The Observer maps the perimeter)
  ↓
RECON_ACTIVE        (The Scanner probes live surface)
  ↓
HYPOTHESIZE         (The Thinker emits typed claims)
  ↓
EXPLOIT             (The Attacker runs test plans)
  ↓
VERIFY              (The Judge confirms or rejects)
  ↓   ↺ if pending hypotheses + budget remaining,
      ↺   loop back to HYPOTHESIZE
BLUE_TEAM           (The Defender writes Sigma + IR)
  ↓
REPORT              (The Storyteller renders the report)
  ↓
HALT
```

The loop is **budget-aware**. It halts on cost cap, iteration cap, or wall-clock cap. No runaway spend. No infinite loops.

The loop is **checkpointed**. After every state transition, a checkpoint is written to `~/.kryon/targets/<slug>/checkpoint.json` (atomic write, Windows-safe). Pause anytime, resume from where you left off.

The loop is **auditable**. Every state transition is logged with cost, duration, and outcome. The audit log is append-only (SQLite triggers block `UPDATE`/`DELETE`).

The loop has one **branching point**: after VERIFY, if there are pending hypotheses and budget remaining, it loops back to HYPOTHESIZE. This lets the agent test more claims when budget allows, without redoing the recon that's already done.

The "learning" is in the structure: each state feeds the next with concrete graph state, not just text. The LLM doesn't have to remember what it found — it reads the graph fresh. The graph persists across runs. Findings compound. Defenses improve.

## The trust model

The framework is designed for adversarial use — running security tools against real systems. That requires trust. Not "trust me, the AI will be careful" — code-enforced trust.

**The knowledge graph is permission-enforced.** Every write goes through a permission check. Only the `verify` subagent can write a `Finding` node. Only the `blue-team` subagent can write defensive artifacts. A buggy or malicious subagent literally cannot promote itself to a confirmed vulnerability — the `GraphStore.upsert_finding(subagent_name="exploit")` call raises `GraphError` before the write.

**Every tool runs in an isolated Docker container.** Read-only root filesystem, dropped Linux capabilities, CPU and memory limits, wall-clock timeout. Network mode is controlled per tool: `none` (no network), `passive` (internet only, not the target), `active` (target + internet), `oob` (out-of-band callback server only). The tool cannot escape its sandbox.

**The audit log is append-only.** SQLite triggers at the database level block `UPDATE` and `DELETE` operations. Every action — every LLM call, every tool run, every graph write, every state transition — is logged with timestamp, actor, target, outcome, and cost. The log can be queried, exported, and integrity-checked.

**Scope is enforced at multiple layers.** Domain matching (exact, apex, wildcard), CIDR for IPs, exclude paths, lookalike detection (`evilexample.com` does not match `example.com`). The authorization check is verbatim — the agent refuses to run without an explicit "I am authorized" confirmation.

**Hardline blocklist.** Patterns for DoS, social engineering, credential exfiltration, and other destructive behaviors are blocked at the prompt level. The LLM is told these are off-limits. Combined with the permission layer, even a clever prompt injection can't get the agent to do destructive things.

**The LLM cannot hide.** Every call has a cost. Every response is parsed and validated against a Pydantic schema. Every graph write is permission-checked. Every state transition is logged. If the LLM produces invalid output, the response is rejected and a retry is attempted. If the LLM tries to write something it shouldn't, the write is blocked. If the LLM calls a tool that doesn't exist, the call is logged and skipped.

The trust model is **not optional**. These are not features you can turn off without breaking the system. The permissions, the audit log, the scope enforcer, the container isolation — they are the system. An AI security tool that doesn't have these is just a more expensive way to run `nmap`.

## How it works

The agent runs in a coordinated loop:

1. **The orchestrator** loads the target, scope, authorization, and configuration. It checks the budget and starts the loop.
2. **Recon** subagents map the attack surface — passive first (no contact), then active (sends traffic under rate limit).
3. **Analysis** reads the knowledge graph and generates typed hypotheses. Each one is a concrete, testable claim.
4. **Exploit** runs the test plans. It uses the tool registry to invoke security tools (sqlmap, nuclei, httpx, nmap, and 60+ more) in isolated Docker containers. It captures evidence.
5. **Verify** re-runs the exploit with a second method, demands reproduction, and either promotes the attempt to a `Finding` or rejects it as a false positive.
6. **Blue-team** generates a Sigma detection rule and IR playbook for each confirmed finding.
7. **Report** synthesizes the results into a professional report.

Every step is logged. Every cost is tracked. Every state is checkpointed. The LLM never invents data — it produces structured output, which is validated and written to the graph. The graph is the source of truth.

The LLM is **configurable**. Anthropic, OpenAI, Ollama (local), Azure, Bedrock, custom endpoints — any provider LiteLLM supports. Set your provider and model, and the system uses it for every subagent.

The tools are **configurable**. 66 tools in the default registry, with per-tool network modes, timeouts, and resource limits. Custom tools can be added via `~/.kryon/config/tools.yaml`. Tools you don't want can be disabled.

The budget is **enforced**. Set a max USD, max iterations, and max wall-clock time. The loop halts when any limit is hit. The cost is tracked per state, so you can see where the money went.

## Built for

**Bug bounty hunters** who want an autonomous first pass on a target. Set the domain, set the rate limit, set the budget. The agent does the recon, generates hypotheses, tests them, and reports findings with paired defenses.

**Penetration testers** who need to be faster without sacrificing rigor. The 9-state loop enforces methodology. The verify gate enforces evidence-based findings. The audit log provides the report trail that clients demand.

**Red teams** that want chain construction and pivoting. The post-exploit subagent looks for combinations. The graph persists across runs, so chains can compound.

**Blue teams** that want paired offensive + defensive research. Every offensive finding comes with a working Sigma rule and an IR playbook. No more "we found this vuln, now what?"

**Security researchers** who need auditable, reproducible AI agent systems. Every LLM call has a cost. Every response is parsed. Every state transition is logged. Replay any run, debug any behavior, audit any decision.

**Engineering teams building with AI** who need to verify their AI-built code is actually secure. The system runs at AI speed, produces structured output, and pairs every vulnerability with the detection that catches it being exploited.

**Students and researchers** studying multi-agent LLM systems. The codebase is open source (MIT), the architecture is documented, the patterns transfer to any domain where structure enables autonomy.

---

## What it is not

It is not a magic "AI fixes all your AI vulnerabilities" button. It's a security testing tool. It runs the same kind of tests a senior pentester would run, but faster and more systematically. The output still requires human review. The Sigma rules still need tuning. The IR playbooks still need to be integrated into the team's actual incident response process.

It is not a replacement for security engineering. It's a force multiplier. The team still needs to triage findings, prioritize fixes, and own the defensive posture.

It is not a tool for attacking systems you don't own. The framework refuses to run without authorization. The scope enforcer blocks out-of-scope actions. The hardline blocklist prevents destructive patterns. The audit log makes every action provable.
